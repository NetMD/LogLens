## 프로젝트 개요

### 배경
Spring Boot/MVC 기반 백엔드 개발자는 운영 환경에서 발생하는 에러를 로그 파일로 진단한다. 그러나 수백 MB에 달하는 로그 파일을 텍스트 에디터로 열어 수작업으로 분석하는 것은 비효율적이며, 기존 클라우드 기반 로그 분석 도구(Datadog, Splunk 등)는 사내 보안 정책상 사용이 어렵거나 비용 부담이 크다. LogLens는 로컬에서 실행되는 데스크탑 앱으로 이 문제를 해결한다.

### 목적
- Spring Boot/MVC 로그 파일을 빠르게 파싱하여 에러 패턴을 시각화한다
- 스택트레이스를 구조적으로 탐색할 수 있는 UI를 제공한다
- 싱글 실행 파일(Tauri)로 설치 부담 없이 배포한다
- 유료 라이선스 모델(프리미엄)로 SaaS 없이 지속 가능한 수익 구조를 구축한다

### 성공 기준
| 기준 | 측정 방법 | 목표값 |
|------|-----------|--------|
| 파싱 성능 | 500MB 로그 파일 전체 파싱 완료 시간 | 30초 이내 |
| UI 반응성 | 파일 드롭 후 파싱 시작까지 | 1초 이내 |
| 라이선스 검증 | 오프라인 유예 기간 내 앱 정상 동작 | 7일 보장 |
| 배포 형태 | 단일 실행 파일 크기 | 50MB 이하 권장 |
| 무료 핵심 기능 | 기본 파싱 및 에러 패턴 시각화 | 라이선스 없이 완전 동작 |

## 핵심 요구사항

### 기능 요구사항 (FR)

#### [로그 파일 입력]
- **FR-01** 사용자는 로그 파일을 드래그앤드롭 또는 파일 탐색기를 통해 불러올 수 있어야 한다 (무료)
- **FR-02** 단일 파일 입력은 무료로 지원하며, 다중 파일 동시 입력은 유료 기능으로 제한한다
- **FR-03** 지원 파일 형식: `.log`, `.txt` (확장자 없는 파일도 허용, MIME 타입 무관하게 텍스트 파일이면 파싱 시도)
- **FR-04** 파일 크기 상한선은 500MB로 제한하며, 초과 시 사용자에게 명확한 오류 메시지를 표시한다

#### [Spring 로그 파싱]
- **FR-05** 파싱 대상 필드: `timestamp`, `level`, `pid`, `thread`, `logger(class)`, `message`, `exception class`, `stacktrace`
- **FR-06** 기준 로그 패턴: `yyyy-MM-dd HH:mm:ss.SSS  LEVEL PID --- [thread] logger.class : message`
- **FR-07** 로그 레벨 분류: `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`, `FATAL`
- **FR-08** Exception 및 StackTrace 블록을 하나의 논리 단위로 묶어 파싱한다 (멀티라인 처리)
- **FR-09** 파싱 중 진행률(0~100%)을 UI에 실시간으로 표시한다
- **FR-10** 500MB 파일을 스트리밍 방식으로 처리하여 메모리 과부하를 방지한다 (Rust 레이어에서 청크 단위 처리)
- **FR-11** 파싱 패턴에 맞지 않는 라인은 파싱 실패 카운트를 집계하되 앱 크래시 없이 건너뛴다

#### [에러 패턴 분석 - 무료]
- **FR-12** Exception 유형별 발생 빈도를 집계하여 Top 10 목록으로 표시한다
- **FR-13** 시간대별 에러 분포를 차트(막대 또는 라인)로 시각화한다 (Recharts 사용)
- **FR-14** 로그 레벨별 전체 건수를 요약 카드로 표시한다 (INFO/WARN/ERROR 등)
- **FR-15** 특정 에러 항목 클릭 시 해당 스택트레이스 위치로 자동 스크롤한다

#### [스택트레이스 뷰어 - 무료]
- **FR-16** 스택트레이스는 구분된 카드/블록 형태로 렌더링하여 가독성을 높인다
- **FR-17** 사용자 코드 라인(`com.example.*` 등 프로젝트 패키지)과 프레임워크 라인을 시각적으로 구분하여 하이라이팅한다
- **FR-18** 스택트레이스 블록은 접기/펼치기(collapse/expand) 가능해야 한다

#### [분석 히스토리 - 유료]
- **FR-19** 분석 결과는 로컬 SQLite에 저장하며, 이전 분석 기록을 목록으로 조회할 수 있다
- **FR-20** 저장된 히스토리는 재로딩 없이 빠르게 불러올 수 있어야 한다 (파싱 재수행 불필요)
- **FR-21** 히스토리 항목별 삭제 기능을 제공한다

#### [다중 파일 비교 분석 - 유료]
- **FR-22** 2개 이상의 로그 파일을 동시에 불러와 에러 패턴을 나란히 비교할 수 있다
- **FR-23** 비교 뷰에서 파일 간 동일 Exception 유형의 발생 빈도 차이를 시각화한다

#### [PDF 리포트 Export - 유료]
- **FR-24** 현재 분석 결과(요약, 에러 Top 10, 시간대 차트)를 PDF 파일로 저장할 수 있다
- **FR-25** PDF에는 분석 일시, 파일명, 파싱된 총 라인 수, 에러 건수가 포함되어야 한다

#### [AI 에러 원인 분석 - 유료]
- **FR-26** 사용자가 본인의 OpenAI 또는 Anthropic Claude API 키를 앱 설정에 입력할 수 있다
- **FR-27** 특정 Exception 선택 후 "AI 분석" 버튼 클릭 시 해당 스택트레이스와 메시지를 프롬프트로 구성하여 API 호출한다
- **FR-28** API 키는 로컬 OS 키체인(Tauri secure storage) 또는 암호화된 로컬 설정 파일에 저장한다
- **FR-29** AI 응답 결과는 해당 에러 블록 하단에 인라인으로 표시한다
- **FR-30** API 호출 비용은 사용자 부담임을 UI에 명시한다

#### [라이선스 시스템]
- **FR-31** 라이선스 키 입력 모달을 제공하며 키 형식은 `LOGLENS-{6자리 영숫자}-{7자리 영숫자}` 패턴을 따른다
- **FR-32** 라이선스 검증 순서: 로컬 캐시 확인 → 캐시 만료(7일 초과) 시 서버 API 호출 → 서버 미응답 시 오프라인 유예 7일 적용
- **FR-33** 서버 검증 API: `POST https://api.loglens.dev/v1/license/verify`
- **FR-34** 유효하지 않은 라이선스 키 입력 시 유료 기능 버튼은 잠금(disabled) 상태로 유지하고 업그레이드 안내 메시지를 표시한다
- **FR-35** 라이선스 상태(유효/만료/오프라인 유예)를 앱 내 상태 표시줄 또는 설정 화면에서 확인할 수 있어야 한다

### 비기능 요구사항 (NFR)

- **NFR-01 성능** 500MB 로그 파일 전체 파싱을 30초 이내에 완료한다 (Rust 스트리밍 파싱 적용)
- **NFR-02 성능** 파싱 완료 후 에러 목록 초기 렌더링은 2초 이내에 완료한다 (가상 스크롤 고려)
- **NFR-03 보안** API 키(OpenAI, Claude)는 평문으로 저장하지 않는다
- **NFR-04 보안** 라이선스 키 로컬 캐시는 단순 파일 저장이 아닌 암호화 또는 난독화 처리한다
- **NFR-05 보안** 외부 API 호출(라이선스 검증, AI 분석)은 HTTPS만 사용한다
- **NFR-06 안정성** 파싱 중 앱 비정상 종료 없이 모든 예외를 처리한다 (파싱 오류는 로그로 수집)
- **NFR-07 호환성** macOS(Apple Silicon/Intel), Windows 10/11, Linux(Ubuntu 22.04+) 빌드를 제공한다
- **NFR-08 배포** Tauri 싱글 실행 파일(.dmg, .exe, .AppImage)로 배포한다
- **NFR-09 접근성** 다크모드를 기본값으로 설정하며, 라이트모드 전환 옵션을 제공한다 (P2)
- **NFR-10 유지보수** 로그 파싱 패턴은 설정 파일 또는 파서 모듈로 분리하여 추후 Logback 외 포맷 확장이 용이하도록 설계한다

## 제약 조건

### 기술 스택 제약
- Frontend: React + TypeScript + TailwindCSS (고정)
- Desktop 런타임: Tauri v2 (Rust) (고정)
- 차트 라이브러리: Recharts (고정)
- 빌드 도구: Vite + pnpm (고정)
- DB: SQLite (로컬 전용, 히스토리 기능 한정)
- 파싱 로직 위치: TypeScript 레이어에서 처리하되, 파일 I/O 및 스트리밍은 Rust Tauri Command 사용

### 아키텍처 제약
- 모든 데이터는 로컬에서 처리한다 (로그 파일을 외부 서버로 전송하지 않음)
- 라이선스 검증 서버(`api.loglens.dev`)는 별도 백엔드 프로젝트로 운영 (본 프로젝트 범위 외)
- AI 분석은 사용자 API 키를 이용한 직접 호출 방식 (프록시 서버 없음)

### 일정 제약
- 초기 명세 기준 개발 우선순위 순서를 따른다 (설정된 9단계 참고)
- MVP 범위: FR-01 ~ FR-18 (무료 기능 전체) + FR-31 ~ FR-35 (라이선스 기반 잠금 UI)

### 리소스 제약
- 라이선스 서버 API(`api.loglens.dev`)는 사전 구축되어 있거나 동시에 개발됨을 전제한다
- AI 분석 기능은 OpenAI/Anthropic API 스펙 변경에 영향을 받을 수 있다

- AI 에러 원인 분석 (FR-26 ~ FR-30)

### P2 - 있으면 좋음

## 명확화가 필요한 사항

다음 항목은 현재 초기 명세에서 정의되지 않았으며, 기획자 또는 의사결정권자의 판단이 필요합니다.

1. **라이선스 가격 정책 및 플랜 구조**
   - 단일 영구 라이선스인가, 연간 구독인가?
   - 개인용/팀용 플랜 구분이 있는가?
   - 라이선스 1개로 몇 대의 기기를 허용하는가?

2. **라이선스 서버 개발 범위**
   - `api.loglens.dev` 백엔드는 이 프로젝트와 동시에 개발되는가, 별도 팀/일정인가?
   - 서버 미구축 상태에서 클라이언트 개발 시 Mock 처리 전략이 필요하다

3. **파싱 패턴 커스터마이징 지원 여부**
   - 사용자가 커스텀 로그 패턴(Logback pattern)을 직접 입력하여 파싱할 수 있어야 하는가?
   - 지원한다면 P1 또는 P2로 분류하여 개발 범위에 포함해야 한다

4. **히스토리 저장 용량 정책**
   - SQLite 히스토리의 최대 보관 건수 또는 기간 제한이 있는가?
   - 용량 초과 시 자동 삭제(오래된 항목 순) 또는 사용자에게 경고하는가?

5. **다중 파일 비교 분석의 최대 파일 수**
   - 동시에 비교 가능한 파일 수의 상한선이 있는가? (권장: 최대 5개)

6. **AI 분석 프롬프트 전략**
   - 스택트레이스 전체를 전송하는가, 요약 정보만 전송하는가?
   - 토큰 비용 최적화를 위한 입력 최대 길이 제한이 필요한가?

7. **앱 자동 업데이트 지원 여부**
   - Tauri의 내장 업데이터(tauri-plugin-updater)를 활용한 자동 업데이트를 지원하는가?
   - 지원 시 업데이트 서버 엔드포인트가 필요하다

8. **로그 파일 인코딩 처리**
   - UTF-8 이외의 인코딩(EUC-KR 등) 파일에 대한 처리 방침이 있는가?

## UX 설계 필요 여부

**판단: YES**

**이유:**
- 신규 화면이 다수 추가된다: 메인 분석 화면, 스택트레이스 뷰어, 에러 패턴 차트 화면, 라이선스 입력 모달, 히스토리 목록 화면, 다중 파일 비교 화면, 설정 화면(API 키 입력)
- 사용자 핵심 플로우가 3단계 이상이다: 파일 드롭 → 파싱 진행 → 결과 탐색 → 에러 상세 → AI 분석
- 무료/유료 기능의 잠금 UI 설계가 필요하며 사용자 전환 유도(CTA) 레이아웃 판단이 요구된다
- 다크모드 기본 + 라이트모드 전환, 가상 스크롤 적용 범위 등 레이아웃 및 컴포넌트 설계 판단이 필요하다

**UX 설계 범위 제안:**
- 전체 화면 플로우 와이어프레임 (파일 입력 → 파싱 → 결과 대시보드)
- 에러 패턴 대시보드 레이아웃 (차트 배치, 요약 카드 구성)
- 스택트레이스 뷰어 컴포넌트 설계
- 라이선스 모달 및 유료 기능 잠금 상태 UI
- 설정 화면 (AI API 키, 라이선스 상태)

## PM 판단 및 의사결정 근거

### 1. 파싱 로직 레이어 분리 결정
파일 I/O와 스트리밍 처리는 Rust(Tauri Command)에서 담당하고, 실제 로그 파싱 로직(정규식, 구조화)은 TypeScript 레이어에서 처리하도록 명시했다. 이는 초기 명세의 의도를 반영하되, Rust에서 전체 파싱을 처리할 경우 TypeScript 단에서의 테스트 및 유지보수가 어렵다는 점을 고려한 판단이다. 추후 성능 이슈 발생 시 Rust로 파싱 로직 이전을 P2로 검토할 수 있다.

### 2. MVP 범위에 라이선스 잠금 UI 포함
유료 기능 잠금/해제 처리를 P0에 포함한 이유는, 무료 기능만 출시하더라도 향후 유료 기능 추가 시 구조 변경 비용이 크기 때문이다. 라이선스 검증 흐름과 기능 잠금 상태 UI는 초기부터 설계하는 것이 타당하다.

### 3. AI 분석은 프록시 없이 직접 호출 방식 유지
사용자 API 키를 통한 직접 호출 방식은 서버 운영 비용을 제거하고 사용자 데이터 프라이버시를 보장한다. 그러나 API 키 노출 위험이 있으므로 NFR-03(보안 저장)을 반드시 준수해야 한다.

### 4. PDF Export를 P2로 분류
PDF 생성은 Tauri 환경에서 별도 라이브러리 통합이 필요하고 구현 복잡도 대비 초기 사용자 가치가 상대적으로 낮다. 히스토리 저장 및 AI 분석이 더 높은 사용자 가치를 제공한다고 판단하여 P2로 분류했다.

### 5. 다크모드 기본 설정의 타당성
타깃 사용자(백엔드 개발자)는 장시간 로그를 보는 환경에서 다크모드를 선호하는 경향이 높다. 다크모드를 기본값으로 설정하는 것은 타깃 사용자 경험에 부합하는 판단이다.

### 6. 오프라인 유예 7일 정책의 명시
라이선스 서버 장애 또는 네트워크 단절 상황에서도 사용자가 7일간 유료 기능을 사용할 수 있도록 보장해야 한다. 이는 개발자 사용 환경(보안망 내부, VPN 등)을 고려한 사용자 친화적 정책이다. 단, 오프라인 유예 만료 후에는 서버 재검증 전까지 유료 기능을 잠금 처리해야 한다.
